# Codex Hybrid Engine — полная карта проекта и дорожная карта

**Срез состояния:** 9 октября 2026 г.  
**Назначение файла:** описать текущие подсистемы, целевой результат, план завершения и честную оценку готовности.  
**Тип документа:** рабочая дорожная карта, не гарантия сроков и не утверждение о выпуске production-релиза.

---

## 1. Краткое резюме

Codex Hybrid Engine — локальный Python CLI и набор вспомогательных инструментов для безопасной передачи задач coding-моделям. Основной цикл проекта:

```text
описание задачи
  → классификация и профиль проекта
  → ограниченный контекст и prompt pack
  → выбор провайдера
  → изолированное выполнение
  → проверки качества и отчёт
  → review
  → явное подтверждение apply
```

Вокруг основного цикла развиваются дополнительные режимы: ручной и автоматизированный браузерный мост к веб-чатам, Visual QA, локальный UI, карта репозитория и адаптеры делегирования.

### Оценка на текущем снимке

- **Готовность реализации дорожной карты: около 69%.** Это взвешенная инженерная оценка по подсистемам ниже, а не измерение из самого приложения.
- **Готовность к надёжному выпуску: около 55%.** Главные причины: известный сбой Windows sandbox у Codex CLI, не завершённая автоматизация DeepSeek, неполная живая проверка провайдеров и QA-режимов, а также незакрытая чистая приёмка всего рабочего дерева.
- **Автоматические тесты:** последний полный прогон в этой рабочей сессии — `224 passed`. Это сильная регрессия, но она сама по себе не заменяет реальные прогоны Codex, Groq/OpenRouter, Chrome, PHP и UI.

Проценты приблизительные. Они учитывают наличие кода, регрессионных тестов, живой проверки и эксплуатационных блокеров; критерии приведены в разделе 8.

## 2. Карта репозитория

| `docs/` | Руководства, архитектурные заметки и QA-отчёты. |

| `.venv/` | Локальное Python-окружение; не часть поставляемого исходного кода. |

### `hybrid/`: подсистемы программы

#### CLI и оркестрация

- `cli.py` — команды `doctor`, `init`, `providers`, `context`, `skills`, `profile`, `run`, `review`, `apply`, `status`, `report`, `browser`, `visual`, `harness`, `map` и `ui`.
- `controller.py` — основной маршрут задачи: классификация, provider selection, запуск, проверки и сохранение результата.
- `tasks.py`, `state.py`, `report.py` — модели задачи, локальное состояние и канонический отчёт с явным `NOT RUN` для непроведённых проверок.
- `config.py` — загрузка настроек, безопасные defaults и фильтрация project-level overrides.

#### Провайдеры моделей

- `providers/base.py` — общий контракт.
- `providers/codex.py` — адаптер Codex CLI и передача ограничений среды.
- `providers/groq.py`, `providers/openrouter.py` — OpenAI-compatible API adapters.
- `providers/mock.py` — локальный провайдер для воспроизводимых тестов без API.
- `integrations/codex_cli_delegate.py` — отдельная интеграция делегирования задач Codex CLI.
- `integrations/deepseek_harness.py` — необязательный Harness adapter; он не должен объявляться рабочим, пока его локальный CLI-контракт не проверен.

#### Изоляция, проверки и применение результата

- `execution/worktree.py` — подготовка изолированной копии/worktree и работа с патчами.
- `quality/checks.py` — проверки путей, зависимостей, синтаксиса и результатов.
- `review` и `apply` — независимая проверка и применение патча только после явного подтверждения `--yes`, повторных проверок и проверки конфликта.

#### Контекст проекта и агентская среда

- `context/file_context.py` — отбор файлов контекста.
- `context/prompt_pack.py` — сборка prompt pack.
- `context/selection.py` — объяснимый выбор skill/profile/context.
- `context/repo_map.py` — эвристическая карта связей PHP/JS/CSS/SQL и поиск связанных файлов.
- `ai-stack/PROJECT_CONTEXT.md` — единые правила проекта.
- `ai-stack/profiles/` — профили `frontend`, `backend-php`, `database`, `fullstack-game`.
- `ai-stack/skills/` — инструкции по стеку, отладке, браузерному тестированию, безопасности и разработке.
- `ai-stack/design/` — дизайн-память: цвета, типографика, компоненты, сетки, анимации и референсы.

#### Browser AI Bridge

- `browser_bridge/controller.py`, `sessions.py`, `session_live.py` — ручные задачи, хранилище и общая Chrome-сессия.
- `prompt_builder.py`, `response_parser.py` — создание запроса и разбор ответа для ручного relay.
- `cdp.py` — минимальный стандартный-library Chrome DevTools Protocol клиент.
- `browser_state.py`, `webchat.py` — диагностика DOM и state machine автоматизированного чата.
- `sites/` — профили сайтов; ChatGPT имеет полноценную базу селекторов, DeepSeek профиль пока частичный и остаётся fail-closed.
- `providers/` — browser providers для ручного/автоматизированного маршрута.
- `chatgpt_ui.py` — совместимый модуль UI-операций ChatGPT.

Два режима намеренно отличаются по риску:

1. **Manual relay:** пользователь сам переносит prompt и ответ между приложениями.
2. **Автоматизация Chrome:** управление подписанной сессией через CDP; отправка требует отдельного явного действия, артефакты должны быть ограничены и редактированы.

#### Visual QA и локальный интерфейс

- `visual/driver.py`, `visual/engine.py` — запуск браузера, съём viewport и запись проверок.
- `local_ui/server.py`, `handlers.py`, `renderer.py`, `security.py` — локальный UI и HTTP-обработчики.

### `tools/`, `docs/`, `outbox/`

- `tools/inspect_live_dom.py`, `chat_state.py`, `chat_dump.py` и ChatGPT probes — сбор реальных данных DOM и диагностик.

- `tools/smoke_*` — быстрые smoke runs для bridge, local UI и Visual QA.
- `docs/BROWSER_BRIDGE.md`, `docs/VISUAL_QA.md`, инструкции установки и QA reports — пользовательские/технические руководства.

Структура выше собрана по дереву исходников, документации и CLI. Codebase-memory MCP-инструменты в этой сессии недоступны; карта не является графом вызовов, автоматически построенным из индекса.

## 3. Что должно быть в итоговой версии

### Целевой пользовательский результат

Пользователь устанавливает Hybrid Engine, указывает проект и задачу, а программа:

1. проверяет окружение и явно показывает недостающие инструменты;
2. классифицирует задачу и объясняет выбранный профиль;
3. включает только разрешённые файлы/skills в контекст;
4. выбирает доступного провайдера согласно настройкам и бюджету;
5. запускает изменение изолированно от рабочей ветки пользователя;
6. выполняет доступные проверки, сохраняя результаты и помечая непроведённые как `NOT RUN`;
7. создаёт reviewable diff и человекочитаемый отчёт;
8. не меняет исходный проект до явного `hybrid apply <TASK-ID> --yes`;
9. повторно проверяет patch и конфликт непосредственно перед apply.

### Целевое техническое состояние

- Чёткие контракты модулей и providers; локальный mock позволяет проверить полный маршрут без сетевых ключей.
- Project settings не могут перенаправить секреты, расширить список контекста, подменить исполняемые файлы или ослабить security policies.
- Состояние задач и отчёты устойчивы к неполной работе процесса; ошибки указывают конкретный этап и безопасный способ восстановления.
- Browser automation сайт-независима через `SiteProfile`; профили используют только доказанные селекторы, а неизвестные состояния блокируют взаимодействие.
- Ответы веб-чата извлекаются только из нового сообщения ассистента; «текст перестал меняться» не считается доказательством завершения генерации.
- Visual QA действительно открывает целевой сайт, снимает предусмотренные viewport, фиксирует console/network проблемы и сохраняет результат.
- Local UI остаётся loopback-first с проверенными endpoint, origin и локальными данными.
- Установка, upgrade, doctor, документация и полный демо-сценарий работают на заявленных ОС и версиях Python.
- Опциональные integrations остаются явно помеченными, пока их внешние зависимости не доступны и не проверены.

## 4. Дорожная карта

Порядок ориентирован на закрытие эксплуатационных блокеров. Сроки не назначены: они зависят от состояния локального Codex CLI, доступности аккаунтов/ключей и окружения для PHP/UI-проверок.

### Этап 0 — зафиксировать воспроизводимую исходную точку (**P0**)

**Цель:** можно однозначно сказать, какие изменения входят в релиз.

- Создать чистый reviewable branch/worktree от согласованной базы.
- Разобрать существующие staged, unstaged и untracked файлы; не включать чужие изменения по умолчанию.
- Установить зависимости из `pyproject.toml` в новом окружении.
- Сохранить полный результат `pytest -q`, версию Python и `hybrid doctor`.
- Проверить wheel/editable install и `hybrid --help`/entry point.

**Критерий выхода:** чистая база, повторяемая установка, зафиксированная матрица тестов/окружения, отсутствие неизвестных изменений в release diff.

### Этап 1 — основной task → patch → apply путь (**P0**)

**Цель:** завершить обещанный продуктовый сценарий без провайдера с платным API.

- Прогнать offline happy path на `mock`: `run → status → report → review → apply`.
- Проверить сбои provider timeout, невалидный patch, запрещённые пути, patch tampering и конфликт с пользовательским diff.
- Проверить безопасный safe mode и fast mode; подтвердить, что ни один путь не записывает в исходный проект до apply.
- Проверить атомарность состояния и понятное восстановление незавершённой задачи.

**Критерий выхода:** повторяемые integration-тесты и демонстрация двух режимов на чистом demo-репозитории; отказ по каждому негативному случаю.

### Этап 2 — восстановить рабочий Codex CLI путь (**P0**)

**Наблюдаемый блокер:** handoff `outbox/HANDOFF_BROWSER_AND_CODEX.md` описывает воспроизводимую ошибку Windows sandbox provisioning (`helper_unknown_error`), мешающую Codex создавать файлы/запускать команды. На стороне движка уже описаны изменения окружения процесса и передача `--sandbox workspace-write`, но это не устраняет сбой backend-а.

- Диагностировать установку/версию Codex CLI и Windows sandbox на временном тестовом репозитории.
- Не обходить проблему отключением sandbox/approval: это запрещённое направление.
- Проверить корректную диагностику и быстрое завершение, если backend недоступен.
- Подтвердить создание patch через Codex в разрешённом sandbox после исправления среды.

**Критерий выхода:** `doctor` и реальная write-задача подтверждают рабочую ограниченную среду; никаких unsafe bypass flags.

### Этап 3 — единая provider-матрица и конфигурация (**P1**)

- Проверить поведение `codex`, `groq`, `openrouter`, `mock` и browser providers отдельно.
- Для API-provider проверять auth, endpoint, модель, timeout и budget до отправки контента.
- Сохранить правило: project config не подменяет trusted Codex command, API base URL, key source и права контекста.
- Уточнить fallback/retry политику: повтор только на transient ошибки, без дублирования оплачиваемой операции.
- Обновить `hybrid providers`/`doctor`, чтобы status был честным: configured, available, authenticated, live-verified.

**Критерий выхода:** smoke-тест каждого реально доступного провайдера и безопасный `NOT RUN`/unavailable для остальных; неизвестный провайдер не запускается по догадке.

### Этап 4 — контекст, skills, project map и prompt pack (**P1**)

- Проверить профиль и selection на representative frontend/backend/database/game задачах.
- Доказать allowlist файлов на границе каждого provider adapter; секретные/неразрешённые файлы не входят в prompt pack.
- Валидировать repo-map связи на demo PHP/JS/CSS/SQL проекте, включая отсутствующие и неоднозначные зависимости.
- Сравнить сгенерированный prompt pack с разрешённым списком файлов и активными skills.
- Описать размер/лимиты контекста и причины исключения файлов.

**Критерий выхода:** воспроизводимые golden tests на 4 профиля; ни один провайдер не получает больше файлов, чем разрешено trusted policy.

### Этап 5 — довести Browser AI Bridge для ChatGPT (**P1**)

- Сохранить manual relay как стабильный fallback.
- На поддерживаемом ChatGPT build проверить live selectors и полный новый диалог без импорта неправильного/user текста.
- Сохранить defensive guards: Canvas/CodeMirror composer exclusion, role label validation, mounted-state readiness, empty composer, localization, submit confirmation и доказательство конца генерации.
- Проверить redaction артефактов, URL/title privacy, ограничение содержимого screenshots и DOM snippets.
- Пройти dry-run без отправки и отдельный согласованный live run с безопасной тестовой задачей.

**Критерий выхода:** новая беседа → отправка только с `--send` → правильный assistant answer → импорт → review; сбои не сохраняют user prompt как ответ.

### Этап 6 — закончить DeepSeek Web automation (**P1, критический неполный контур**)

**Уже подтверждено:** URL формы `/a/chat/s/<id>`, видимый composer `textarea[name="search"]`; ложный challenge из скрытого `One more step` устранён использованием `innerText` и проверки видимости `#cf-overlay`.

**Осталось снять с живой страницы:**

- send control после заполнения composer;
- assistant-only message wrapper и answer body;
- stop/generation state и точный сигнал завершения;
- message key/baseline, чтобы извлекался новый ответ, а не prompt/история;
- new-chat route/control; локализованные login/rate-limit/error признаки;
- роль меток ответа и реальные DeepSeek response render states, включая код.

Нужна доступная беседа, где реально видны её сообщения и ответ. Пока этого нет, профиль остаётся fail-closed: сохранённый composer-selector не даёт разрешения на отправку.

**Критерий выхода:** таблица live-селекторов с наличием, видимостью, `textLen` и текстовым head; проверка DOM-структуры ответа; тесты profile и state machine; dry-run; затем согласованный prompt в аккаунте и доказанный результат `browser read --json`/import. Не решать CAPTCHA и не отправлять сообщения без прямого разрешения пользователя.

### Этап 7 — Visual QA и PHP/full-stack verification (**P1/P2**)

- Установить/обнаружить заявленные инструменты и корректно различать `NOT FOUND`, `NOT RUN`, fail и pass.
- На demo PHP-проекте провести Visual QA на desktop/tablet/mobile viewport.
- Проверить screenshot, браузерную консоль, failed requests и UI состояния empty/loading/error/disabled.
- Добавить функциональные проверки backend/PHP и SQL только в окружении с PHP/MySQL; не подменять живую проверку статическим тестом.

**Критерий выхода:** записанный визуальный отчёт и скриншоты всех обязательных viewport; функциональные проверки либо прошли, либо отчёт ясно перечисляет внешние блокеры.

### Этап 8 — Local UI и Harness adapter (**P2**)

- Провести security review Local UI: loopback bind, origin/host проверки, CSRF-подобные сценарии, опасные маршруты, открытие браузера и раскрытие локальных файлов.
- Проверить запуск и остановку, восстановление задач, параллельные запросы и понятные ошибки.
- Оставить Harness integration выключенной по умолчанию, пока не подтверждены локальный бинарник, CLI contract, sandbox, output path и результат без обхода политик.

**Критерий выхода:** local UI проходит smoke и security tests; Harness reports «disabled/unverified» до реальной проверки и становится enabled только после неё.

### Этап 9 — релизный контур (**P2**)

- Проверить Windows и Linux install/upgrade для Python 3.11+.
- Зафиксировать поддерживаемые версии Chrome, Codex CLI, PHP и опциональных сервисов.
- Добавить/актуализировать CI: полный тестовый набор, syntax/type checks если проект их принимает, package build и smoke на mock.
- Синхронизировать README, `PROJECT_CONTEXT.md`, docs, CLI help и `doctor`.
- Сформировать changelog, миграции локального task state, правила backup/cleanup `.hybrid`.
- Отдельно провести security review перед объявлением production-ready.

**Критерий выхода:** чистая установка из release artifact, полный CI, mock demo, ограниченный Codex smoke, release notes и отсутствие необъяснённых изменений.

## 5. Приоритеты и зависимости

## 6. Оценка готовности по подсистемам

| Подсистема | Вес | Готовность | Основание и ключевой остаток |
|---|---:|---:|---|
| CLI, task lifecycle, report/apply | 20% | 85% | Широкий набор команд и тесты; нужен чистый end-to-end acceptance на mock и проверка восстановления/конфликтов на чистой базе. |
| Providers и Codex execution | 15% | 65% | Адаптеры есть; Windows sandbox blocker остаётся, API-provider live credentials не подтверждены. |
| Config, isolation, safety gates | 15% | 82% | Присутствуют защитные правила и regression tests; нужен итоговый независимый security review всей текущей базы. |
| Context, skills, profiles, repo map | 10% | 80% | Реализованы общий контекст, профили и карта; надо проверить allowlist на всех provider boundaries и качество map на разных репозиториях. |
| Browser bridge — ChatGPT | 10% | 78% | Есть state machine и регрессии; требуется воспроизводимая live-приёмка в актуальной Chrome-сессии. |
| Browser bridge — DeepSeek | 10% | 35% | Профиль и CAPTCHA false-positive fix есть, composer живьём измерен; send/answer selectors и E2E отсутствуют. |
| Visual QA / PHP verification | 5% | 60% | Инструмент и тесты есть; живая PHP/full-stack проверка зависит от локальных runtime/dependencies. |
| Local UI | 5% | 70% | Реализация и тесты есть; необходим полный локальный threat review и install smoke. |
| Harness adapter | 5% | 30% | Код/тесты есть, но внешний локальный контракт намеренно не подтверждён и integration disabled. |
| Установка, документация, release | 5% | 60% | README и технические документы обширны; нет завершённой чистой release-приёмки и синхронной матрицы платформ. |
| **Итог (взвешенно)** | **100%** | **≈69%** | Округлённая оценка текущей реализации. |

## 7. Definition of Done для программы

Проект можно считать готовым к первому надёжному релизу, когда выполнены все пункты:

- [ ] Чистая воспроизводимая установка и `hybrid doctor` на заявленных ОС.
- [ ] Полный `pytest -q` проходит на чистой базе; CI повторяет проверку.
- [ ] Offline/mock цикл `run → review → report → apply` проверен от начала до конца.
- [ ] Патчи применяются только после явного подтверждения и отказоустойчивы к изменённому патчу/конфликту.
- [ ] Codex CLI пишет только в предусмотренной sandbox среде; sandbox/approval не обходятся.
- [ ] Для активных API провайдеров проверены auth/model/timeout/budget; недоступные честно помечаются.
- [ ] Trusted context allowlist соблюдается на каждой provider boundary.
- [ ] ChatGPT browser automation читает только новый ответ и имеет проверенный сигнал окончания генерации.
- [ ] DeepSeek либо проходит live selector/E2E acceptance, либо явно остаётся unsupported для automation; не может «молча» отправить сообщение.
- [ ] Visual QA smoke работает и сохраняет полезные screenshot/report artifacts.
- [ ] Local UI проходит security review и использует только безопасный локальный bind по умолчанию.
- [ ] Harness остаётся отключённым, пока его локальная sandboxed интеграция не доказана.
- [ ] Отчёты никогда не выдают непроведённую проверку за успешную.
- [ ] Итоговый diff не содержит необъяснённых файлов, пользовательские данные не попали в репозиторий, документация совпадает с CLI.

## 8. Как трактовать проценты и обновлять roadmap

1. Обновлять дату снимка и число полного тестового прогона после каждого крупного этапа.
2. Увеличивать готовность только по проверенному критерию выхода: тестом, демонстрацией или зафиксированной живой проверкой.
3. Если зависимость отсутствует, отмечать точный статус (`NOT FOUND`, `NOT CONFIGURED`, `NOT RUN`) и не занижать риск формулировкой «почти готово».
4. Не включать staged/unstaged/untracked работу других агентов в релизную оценку, пока не установлено её происхождение и она не прошла review.
5. Пересчитывать итог как сумму `вес × оценка`; отдельно указывать процент реализации и процент эксплуатационной готовности, когда они расходятся.

### Примечание о снимке рабочего дерева

На дату оценки рабочее дерево содержит незакоммиченные и неотслеживаемые изменения нескольких подсистем и файлов, включая дополнительные материалы в `outbox/`. В этом проекте изменения применяются и коммитятся человеком. Перед релизом необходимо установить точную базу каждого изменения и сформировать отдельный reviewable diff; эта roadmap сама по себе не утверждает, что всё содержимое текущей папки уже является единым принятым релизом.
